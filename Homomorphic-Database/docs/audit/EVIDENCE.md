**Purpose:** give an independent reviewer everything needed to verify the
claims in this repository without asking us for missing context. This is the
stage-1 deliverable (roadmap C6); it is evidence, not an audit.

**Measurement point:** 2026-11-10, worktree on top of commit `3408d55`, on the
machine described in `PROJECT_STATUS.md` §1. Nothing in this worktree has been
committed or published.

## 1. How to verify this pack

```bash
# From the repository root. Checks every frozen artifact below.
sha256sum -c docs/audit/evidence.sha256
```

`evidence.sha256` is regenerated by `docs/audit/refresh_evidence.sh`. It covers
artifacts whose bytes are frozen for the review — the golden corpus, the
vendored TFHE-rs manifest, and `Cargo.lock`. Ordinary source files are
deliberately **not** hashed there: they change during remediation and stale
hashes would make the manifest meaningless. Cite a commit hash for source.

## 3. TFHE-rs patch verification

The repository vendors TFHE-rs 1.7.0 because its published `crate-type`
declaration makes cargo build a cdylib that no PE/COFF linker can produce: the
DLL exports 165,566 symbols, above the 65,535-ordinal limit. The project links
`tfhe` only as an rlib, so the vendored copy declares `crate-type = ["lib"]`.
**No cryptographic source is modified.** Verify that claim:

```bash
# 1. Fetch the published archive and record its hash.
curl -sSL -o tfhe-1.7.0.crate https://static.crates.io/crates/tfhe/tfhe-1.7.0.crate
sha256sum tfhe-1.7.0.crate
# f341a7a6fe90bf813ecb2b098f04c0e5bca82436ddd1b256e6f1ec68be58da52  tfhe-1.7.0.crate

# 2. Extract, and compare content while ignoring line endings
#    (the checkout has CRLF; the published archive has LF).
tar -xzf tfhe-1.7.0.crate
diff -r --brief --strip-trailing-cr tfhe-1.7.0 vendor/tfhe
# Only in vendor/tfhe: .cargo-ok
# Files tfhe-1.7.0/Cargo.toml and vendor/tfhe/Cargo.toml differ

# 3. The source tree itself is identical.
diff -r --brief --strip-trailing-cr tfhe-1.7.0/src vendor/tfhe/src
# (no output; exit 0)

# 4. The only manifest change is the crate type.
diff -u --strip-trailing-cr tfhe-1.7.0/Cargo.toml vendor/tfhe/Cargo.toml
# -crate-type = ["lib", "staticlib", "cdylib"]
# +crate-type = ["lib"]
```

Observed on 2026-11-10: 1,674 files in the published archive, 1,675 in the
vendor tree (the extra file is cargo's `.cargo-ok` marker); the source diff is
empty. `vendor/tfhe/.cargo_vcs_info.json` records upstream commit
`4267a92fbd462f22ac05a906418edd00f709355d`.

Why this matters to the review: every cryptographic primitive the database uses
comes from this exact upstream source. The patch cannot hide a change in the
primitives, and the workspace pins it with `[patch.crates-io] tfhe = { path =
"vendor/tfhe" }`.

## 4. Parameter provenance

The parameter set is TFHE-rs 1.7.0's
`PARAM_MESSAGE_2_CARRY_2_KS_PBS_TUNIFORM_2M128` (vendor name "2M128"). Values,
where they are declared in this repository, and what pins them:

| Parameter | Value | Provenance |
|---|---|---|
| LWE dimension | 918 | `SecurityParameters::pinned_default`, `crates/fhe-core/src/keys.rs:148-162` |
| GLWE dimension | 1 | same |
| Polynomial size | 2048 | same |
| PBS base log / level | 23 / 1 | same |
| KS base log / level | 4 / 4 | same |
| Message / carry modulus | 4 / 4 | same |
| Max noise level | 5 | same |
| `log2(p_fail)` | -129.581 | same; vendor value is `-129.58` |
| TFHE-rs definition | `PARAM_MESSAGE_2_CARRY_2_KS_PBS_TUNIFORM_2M128` | `vendor/tfhe/src/shortint/parameters/v1_4/classic/tuniform/p_fail_2_minus_128/ks_pbs.rs:29-43` |
| Key generation | `ConfigBuilder::default().build()` | `crates/fhe-core/src/keys.rs:39-42` |

Enforcement: `default_parameters_match_documented_pinning` reads the parameters
back out of a generated `ClientKey` and fails if any value drifts, and
`crates/fhe-core/tests/format_freeze.rs::documented_security_parameters_are_frozen`
pins the same values for the audit.

**Claim boundary.** "128-bit IND-CPA^D" is TFHE-rs's label for this parameter
set, derived with the Lattice-Estimator. This repository does not reproduce the
estimate, does not implement IND-CPA^D, and holds no independent proof. The
review should treat the label as a vendor claim to be checked, not as a project
result. See [`PARAMETERS.md`](PARAMETERS.md).

## 5. Wire and key formats

**Ciphertext envelope v1** (`crates/fhe-core/src/ciphertext.rs`):

```
bincode struct CiphertextEnvelope {
    version: u8,          // CURRENT_ENVELOPE_VERSION = 1  (ciphertext.rs:25)
    width:   ScalarWidth, // U8 | U16 | U32 | U64 tag
    payload: Vec<u8>,     // bincode of the TFHE-rs ciphertext
}
```

`Ciphertext::from_envelope_bytes` (`ciphertext.rs:234`) does **not** hand the
whole buffer to bincode: `parse_envelope_header` validates the fixed prefix and
declared payload length, and `check_payload_lengths` bounds internal length
prefixes before allocation. A 64 MiB cap rejects oversized envelopes. These are
the paths the fuzz targets exercise (`fuzz/fuzz_targets/fuzz_envelope.rs`).

**Key serialization** (`keys.rs`): `ClientKey::to_bytes` / `ServerKey::to_bytes`
are bincode of the TFHE-rs key. Deserialization uses fixint encoding, a limit
equal to the input length, and `reject_trailing_bytes`, so a short buffer
cannot make bincode allocate from an attacker-chosen length. Keys are
redacted in `Debug`.

**Golden corpus semantics:** `v1_envelope_u32_42.bin` is a `U32` ciphertext of
`42` under `v1_client_key.bin`; `golden_corpus.rs` decrypts it and asserts
`42`. The corpus is the independent known-answer artifact for the frozen
format; its hashes are in §2 and in `format_freeze.rs`.

## 6. Key lifecycle (what is actually implemented)

| Stage | Implementation | Evidence |
|---|---|---|
| Generation | Client-side only; `ClientKey::new()` → `(ClientKey, ServerKey)`; the secret key never leaves the client | `crates/fhe-core/src/keys.rs:39-42`; `examples/encrypted_sum` |
| Server key transfer | `POST /keys/server`, raw bytes, installed in `AppState`; the secret key is never an API input | `crates/fhe-server/src/routes.rs` `upload_server_key` |
| Phone storage | `(ClientKey, ServerKey)` encrypted with AES-256-GCM under a pinned, recorded Argon2id PIN-derived key in a single atomic `vault.json` v2 under `%APPDATA%/FHE-DB` | `apps/fhe-phone/src/keystore.rs`; [`KEY_LIFECYCLE.md`](KEY_LIFECYCLE.md) |
| Backup / restore | PIN-protected v2 export/import (v1 backups accepted); one atomic commit; the PIN hash travels with the encrypted key material | same; residuals below |
| Rotation | Not implemented for the FHE key pair; a new keypair invalidates existing ciphertexts by design | `docs/audit/KEY_LIFECYCLE.md` |
| Destruction | Wired `vault.destroy {pin}` IPC and Settings control; erases the vault atomically and drops in-memory key/PIN | `apps/fhe-phone/src/engine.rs` `vault_destroy`; `KeyStore::destroy`; test `destroy_removes_local_key_material` |

Lifecycle findings **F4 and F8 are fixed** (2026-11-11): the KDF parameters are
pinned and persisted, the PIN floor is 6 digits with a digits-only policy,
unlock failures are rate-limited and persisted, key buffers are zeroized where
the libraries allow, PIN change/import/destruction are single atomic commits,
and a legacy v1 two-file store is migrated. Residuals, disclosed rather than
fixed: an offline attacker with a copied vault can still guess the PIN (the
backup contains the hash), there is no memory locking, and TFHE-rs key types do
not expose zeroization. See [`KEY_LIFECYCLE.md`](KEY_LIFECYCLE.md) §7–8 for the
test matrix and limits.

## 7. Reproduction commands

Run from the repository root. FHE workloads are slow in debug; use `--release`.

```bash
# Quality gate
cargo build --release --workspace
cargo test --release --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check

# Phone keystore matrix (vault v2, migration, lockout, atomicity, destroy)
cargo test -p fhe-phone --release

# Frozen formats (the audit gate)
cargo test --release -p fhe-core --test format_freeze
cargo test --release -p fhe-db --test format_freeze

# Known-answer corpus
cargo test --release -p fhe-core --test golden_corpus

# End-to-end demos
cargo run --release -p encrypted_sum     # SUM 325000, AVG 65000, COUNT 5/5
cargo run --release -p encrypted_nn      # XNOR truth table 4/4
cargo run --release -p encrypted_iris    # plaintext 29/30 = encrypted 29/30

# Dependency boundary: tfhe's only workspace parent must be fhe-core
cargo tree -i tfhe --workspace --edges normal

# Durability against the real binary (graceful stop, hard kill, torn tail)
cargo test --release -p fhe-server --test durability

# WAL recovery observability: the runbook's event names and fields
cargo test --release -p fhe-server
```

**Measured 2026-11-10** on this worktree: `cargo test --release --workspace` →
**119 passed, 0 failed, 1 ignored** (the ignored test regenerates the golden
corpus and is run only on a deliberate format change); build, clippy
(`-D warnings`), and fmt all clean. The audit gates alone:
`cargo test --release -p fhe-core -p fhe-db --test format_freeze` → **5 passed**.
Full results are recorded in `PROJECT_STATUS.md` §1 and
[`README.md` §Executed evidence](README.md#executed-evidence). Anything not run
there (TLS feature, fuzz targets, Criterion benchmarks, phone GUI) is stated as

### Reproducing the two live security probes

Both probes use the release binary and the committed golden envelope, so they
do not need a keypair:

```bash
cargo build --release -p fhe-server

# F1: rate limiter is per-IP, not per-connection (expensive quota = 120/min).
# Start the server on 127.0.0.1:18084, then issue 125 requests each on a new
# connection to /models/xnor/infer. Expect 120 handled (409 NO_MODEL before a
# model is installed) and 5 x 429.

# F2: a rejected mutation leaves no WAL record.
# Start with --data-dir, create a table with a U16 column, POST the committed
# U32 golden envelope into it. Expect 400 WIDTH_MISMATCH and an unchanged log
# size; a forced restart must serve the committed table, not fail replay.
```

## 9. What this pack does not establish

- That the TFHE parameters are secure, or that the 128-bit label is correct.
- That the implementation is free of timing, memory-disclosure, or
  cryptanalytic defects. That is what the external review is for.
- That the phone GUI was exercised in the measured baseline. The keystore's
  F4/F8 fixes are covered by dedicated tests; residual offline PIN guessing and
  vendor zeroization limits are disclosed, not solved.
- That the server is safe to expose: no authorization/tenancy (F9), permissive
  CORS, and a shared bearer token.
- That the audit has happened. Outreach is prepared in
  [`ENGAGEMENT.md`](ENGAGEMENT.md); no reviewer has been engaged.
