## Challenge 1: Mobile OS Limitations on "Signal Isolation"

### The Constraint

Mobile operating systems strictly limit non-system apps from programmatically toggling system-wide radios (Wi-Fi, Cellular, Bluetooth, NFC) due to security sandboxes and accessibility guidelines.

- **iOS:** `NEHotspotConfigurationManager` cannot disable cellular. `CTCellularPlan` is restricted. No public API exists for programmatic Airplane Mode.
- **Android:** `TelephonyManager.disableRadio()` and `WifiManager.setWifiEnabled()` are deprecated/restricted from API 29+. `ConnectivityManager` reports state but cannot toggle.

### Impact

Relying on programmatic radio kill as the primary mechanism will:
1. Fail silently on newer OS versions where APIs are restricted
2. Cause App Store / Play Store rejection for attempting to use private APIs
3. Provide false security confidence — the app thinks radios are off when they aren't

### Recommendation (v1.1)

**Restructure signal isolation to UI-prompt-first architecture:**

1. **Primary path:** Display full-screen modal instructing user to enable Airplane Mode, with live `NWPathMonitor` / `ConnectivityManager` polling to detect compliance. App refuses to decrypt genome until connectivity = none.
2. **Secondary path:** Attempt platform-appropriate programmatic disable as a best-effort supplement, never as the sole mechanism.
3. **Emergency path:** 500ms poll loop during genome operations. If connectivity detected, immediately zero out genome buffers, re-encrypt, and terminate the operation.
4. **Verification:** Before any genome operation, log the method used (user-enabled vs programmatic) for audit.

```rust
// v1.1 Signal Isolation flow (pseudocode)
fn ensure_signal_isolation() -> Result<(), IsolationError> {
    // 1. Show UI prompt for Airplane Mode
    show_airplane_mode_dialog();
    
    // 2. Poll for compliance (max 30 seconds)
    let start = Instant::now();
    while start.elapsed() < Duration::from_secs(30) {
        if !has_network_connectivity() {
            return Ok(()); // User complied
        }
        sleep(500ms);
    }
    
    // 3. Attempt programmatic disable as supplement
    let pgm_result = try_programmatic_radio_disable();
    
    // 4. Final check
    if has_network_connectivity() {
        return Err(IsolationError::RadioActive);
    }
    Ok(())
}
```

## Challenge 2: zk-SNARK Performance Constraints on Mobile Hardware

### The Constraint

Running Groth16 witness generation or PLONK proving steps over Merkle trees with depth ~22 (~4M variants) is memory- and CPU-intensive. Mobile constraints:

- **iOS jetsam limit:** ~2-3GB memory; witness generation for large circuits can exceed this
- **Thermal throttling:** Sustained computation causes SoC temperature to hit throttle threshold, increasing proof time 3x+
- **Background task termination:** iOS watchdog kills apps after ~30s background execution; Android `WorkManager` has similar limits
- **Battery drain:** Generating a single Groth16 proof on mobile SoC draws 3-5W sustained; user battery drops 20%+ per proof

### Impact

- Proof generation times exceeding 30 seconds lead to user abandonment
- App killed by OS mid-proof forces full restart (no checkpoint)
- Users disable app or leave negative reviews due to battery drain
- VariantCount circuits with k=100 variants may be impractical on mobile

### Recommendation (v1.1)

**Multi-layered mobile optimization strategy:**

1. **Pre-computation during idle/charging:**
   - When device is plugged in and on Wi-Fi, pre-compute the Poseidon Merkle tree root
   - Cache intermediate witness data to reduce proof generation time by ~60%
   - Use `BGProcessingTask` (iOS) / `WorkManager` (Android) for background scheduling

2. **Proof splitting & checkpointing:**
   - Split large circuits (VariantCount) into chunks of 10 variants max
   - Save proof state at each chunk boundary for resume capability
   - Target: max 5 seconds per chunk, 50 seconds total for worst case

3. **Explore alternative proving systems:**
   - **Noir** — Domain-specific language for zk proofs; compiles to PLONK; better mobile performance
   - **Halo2** — Recursive proof composition; no trusted setup; larger proofs but better constraints
   - **STARKs** — No trusted setup; post-quantum; but larger proof sizes (~100KB vs ~200B)

4. **GPU/Metal acceleration:**
   - Implement MSM (multi-scalar multiplication) on GPU via Metal (iOS) / Vulkan (Android)
   - Rust FFI can call Metal Performance Shaders for parallel field operations
   - Target: sub-3 second proof time for HasVariant circuit

```rust
// v1.1 Checkpoint-based proof generation
struct ProofCheckpoint {
    circuit: Circuit,
    completed_chunks: usize,
    intermediate_witness: Vec<u8>,
    cached_merkle_paths: Vec<[u8; 32]>,
}

impl Prover {
    fn prove_with_checkpoints(
        &self, query: &ZkQuery, variants: &[u8], pk: &[u8],
    ) -> Result<ZkProof, ProverError> {
        // Load checkpoint if exists
        if let Some(cp) = self.load_checkpoint(query) {
            return self.resume_from_checkpoint(cp, variants, pk);
        }
        // Fresh proof generation with periodic saves
        let result = self.prove(query, variants, pk)?;
        self.save_checkpoint(&result);
        Ok(result)
    }
}
```

## Challenge 3: Trusted Setup & Circuit Flexibility Trade-offs

### The Constraint

Groth16 requires a per-circuit trusted setup ceremony. Each time circuit parameters change (e.g., new variant types, updated query format), a new ceremony is needed.

- **HasVariant circuit:** Fixed parameters — ceremony needed once per circuit version
- **VariantCount circuit:** Variable k parameter — may need multiple ceremony sizes
- **GenotypeMatch circuit:** Fixed parameters — similar to HasVariant

### Impact

- Updating query parameters or genomic circuit definitions requires app-wide circuit replacements
- Each new circuit version requires a new Powers of Tau ceremony (or contribution ceremony)
- Solo developer cannot credibly run a secure multi-party computation (MPC) ceremony
- Users must download new proving keys with each app update

### Recommendation (v1.1)

**Standardize on universal setup proof systems:**

1. **Primary: PLONK + universal reference string**
   - Single setup for all circuits (no per-circuit ceremony)
   - Larger proofs (~300 bytes vs ~200 bytes) but acceptable for mobile
   - Supported by arbitrary circuits, no ceremony per template change

2. **Secondary: STARKs for circuits requiring no setup**
   - Complete elimination of trusted setup
   - Post-quantum secure natively
   - Tradeoff: proof size (~100KB vs ~200B) — acceptable for Wi-Fi submission

3. **Circuit upgrade path:**
   - Version all circuits with semantic versioning
   - Bundle proving keys with app binary (not downloaded)
   - On new circuit version, retain old keys for pending proofs, switch to new for new queries

```rust
// v1.1 Universal setup selection
fn select_proving_system(circuit_id: &str) -> ProvingSystem {
    match circuit_id {
        // PLONK for all genomic circuits (universal setup)
        "has-variant" | "variant-count" | "genotype-match" => ProvingSystem::Plonk,
        // STARKs for aggregate queries (no setup, PQ secure)
        "dp-aggregate" => ProvingSystem::Stark,
        // Default to PLONK
        _ => ProvingSystem::Plonk,
    }
}
```

## Challenge 4: Phenotypic Context for Pharma Adoption

### The Constraint

Pharmaceutical researchers rely heavily on deep, un-truncated phenotypic data alongside genomic variants. Pure variant presence (HasVariant) is often insufficient without clinical metadata.

- **GWAS studies** require age, sex, BMI, disease state, biomarkers, medication history
- **Clinical trials** need specific inclusion/exclusion criteria matched to genomic data
- **Rare disease research** requires phenotype-genotype correlation

### Impact

- Pharma researchers cannot use ZKG for most real studies without phenotypic data
- Cost reduction from $50,000 to $500 is compelling, but zero utility = zero adoption
- Users may be willing to share phenotypic data but need privacy guarantees for it

### Recommendation (v1.1)

**Incorporate verifiable credentials (VCs) for phenotypic traits:**

1. **Phenotypic VC schema:**
   - Define W3C Verifiable Credential schema for common phenotypic traits
   - Age range (not exact age), BMI range, disease state (ICD-10 coded)
   - Issued by healthcare providers or self-attested with cryptographic binding

2. **zk-proofs over phenotype + genotype:**
   - Extend circuit to take `phenotype_hash` as additional public input
   - Prove "user has variant X AND is in age range Y-Z AND has condition W"
   - Phenotype VC is verified alongside the genome commitment

3. **Selective disclosure:**
   - User can granularly choose which phenotypic traits to reveal
   - Each trait has its own VC that can be independently presented
   - Privacy budget applies to phenotypic queries as well

```solidity
// v1.1 Phenotype-aware query structure
struct PhenotypeQuery {
    bytes32 queryId;
    bytes32 genomicCircuitId;
    bytes32 phenotypeRoot;  // Commitment to required phenotypes
    uint256 rewardPerProof;
    uint256 maxSubmissions;
}
```

## Challenge 5: PLONK Proof Gas Costs on L2 EVM

### The Constraint

PLONK proofs (~300 bytes) are verified on-chain via a pairing check that costs approximately 300,000–500,000 gas per proof on EVM-compatible L2s (Arbitrum, Optimism, Base). While L2 gas is cheap relative to L1 (~0.1 gwei vs ~10 gwei), the cost compounds at research-scale volumes:

| Scenario | Proofs | Gas per Proof | Total Gas | L2 Cost (0.1 gwei) |
|----------|--------|---------------|-----------|---------------------|
| Single HasVariant query | 1 | 350K | 350K | ~$0.01 |
| GWAS study (500 proofs) | 500 | 350K | 175M | ~$5.25 |
| Rare-variant study (10K proofs) | 10,000 | 350K | 3.5B | ~$105 |
| Pharma cohort (100K proofs) | 100,000 | 350K | 35B | ~$1,050 |

At scale, gas costs approach 2–10% of the total research budget, eroding the cost advantage over centralized alternatives.

Additional constraints:
- **L2 data availability fees:** Posting proof data to L1 incurs additional ~5,000–10,000 gas per transaction regardless of proof size
- **Arbitrum Nitro:** Geth-compatible but no native proof aggregation — each proof is a separate EVM call
- **Optimism:** Similar structure; proof verification is dominated by BN254 pairing gas cost
- **zkSync Era/Scroll:** Native zk-rollups could verify proofs at lower cost but introduce platform dependency

### Impact

- At 500 proofs/GWAS study, verification gas is ~$5 — negligible. At 100K proofs, it's ~$1,050 — material.
- Pharma researchers comparing costs: centralized API call ($0.001/query) vs on-chain verification ($0.01/proof) — a 10x premium at small scale
- Gas costs are unpredictable during network congestion; pharma budgets are fixed
- If ZKG tokens are used for gas, token price volatility adds another layer of cost uncertainty

### Recommendation (v1.1+)

**Batch verification and alternative L2 strategy:**

1. **Batch proof verification via multi-pairing:**
   - Verify multiple PLONK proofs in a single EVM call using batch pairing (`BatchVerify` contract)
   - Gas cost for N proofs: O(N) individual vs O(N log N) batched — ~30% savings at N=10, ~50% at N=100
   - Requires proofs to share the same verification key (true for same-circuit proofs)

2. **Deploy to zk-native L2s:**
   - **zkSync Era:** Native proof verification infrastructure; projected ~5,000 gas per PLONK proof
   - **Scroll:** Similar zkEVM architecture; native proof aggregation at L2 level
   - **Migration cost:** Smart contracts written in Solidity are portable; only deployment target changes

3. **Off-chain verification with on-chain settlement:**
   - Verification node network (off-chain) validates proofs and aggregates results
   - Only the aggregate result and a Merkle root of valid proof hashes are posted on-chain
   - Gas cost: one L2 transaction per batch (~21,000 gas) regardless of proof count
   - Tradeoff: introduces trust in verification nodes (mitigated by stake slashing)

4. **Compressed proof formats:**
   - Explore SnarkPack-style proof aggregation (used by Filecoin) — packs N PLONK proofs into one
   - Existing implementations: `snarkpack` Rust library (https://github.com/filecoin-project/snarkpack)
   - Estimated gas per aggregated proof (N=100): ~500K gas — a 70x reduction vs 100 individual proofs

```solidity
// v1.1+ Batch verification contract
contract BatchVerifier {
    // Verify N PLONK proofs sharing the same verification key
    function batchVerify(
        bytes calldata vk,           // Shared verification key
        bytes[] calldata proofs,     // N individual proofs
        bytes32[] calldata publicInputs
    ) external returns (bool) {
        require(proofs.length == publicInputs.length, "Mismatch");
        // Multi-pairing batch check: O(N log N) gas
        return Plonk.batchVerify(vk, proofs, publicInputs);
    }
}
```

## Challenge 6: STARK Migration Roadmap — Managing ~100KB Proofs Over Mobile

### The Constraint

STARK proofs offer two critical advantages over PLONK/Groth16 — no trusted setup and post-quantum security — but at a ~500x increase in proof size:

| Metric | PLONK | Groth16 | STARK (FRI-based) |
|--------|-------|---------|-------------------|
| Proof size | ~300 B | ~200 B | ~100 KB |
| Setup | Universal | Per-circuit | None |
| Post-quantum | No (pairings) | No (pairings) | Yes |
| Verification gas (L2) | ~350K | ~250K | ~5M |
| Prover time (mobile) | ~5s | ~3s | ~60s |

For mobile users, uploading 100 KB over:
- **Wi-Fi:** ~0.5 seconds — acceptable
- **5G:** ~1–2 seconds — acceptable
- **4G/LTE:** ~3–5 seconds — borderline
- **3G/weak signal:** 15–30 seconds — unacceptable user experience
- **Satellite / emergency:** Impractical

Additional constraints:
- **Mobile data caps:** Each STARK proof consumes ~0.1% of a typical 10GB monthly plan. At 100 proofs/month, that's 10MB — negligible. But the latency is the primary UX concern.
- **App store review:** Proof generation taking >60s on mobile will trigger watchdog termination on iOS (~30s background execution limit)
- **Device fragmentation:** Mid-range Android devices may take 2-3x longer for STARK proving than flagship iPhones

### Impact

- Pure STARK proofs on mobile are impractical for real-time (sub-10s) queries
- Users on cellular networks experience frustration with large uploads
- STARK's post-quantum security is valuable for 70+ year privacy horizons, but the UX cost is high
- Verifying STARK proofs on L2 EVM is ~15x more expensive than PLONK, negating the setup benefit

### Recommendation (v1.1+)

**Optimistic batching and recursive STARK composition:**

1. **Recursive proof composition (STARK-in-STARK):**
   - Generate N individual STARK proofs on-device (~60s each, background)
   - Compose N proofs into 1 proof via recursive STARK verifier
   - Final proof size: ~100 KB (same as single), regardless of N
   - Effective per-proof size: 100 KB / N — for N=100, ~1 KB per proof
   - Tradeoff: additional proving time for composition (~120s for N=100)

2. **PLONK-first with STARK fallback:**
   - Default proving system: PLONK (fast, cheap, small proofs)
   - For queries requiring post-quantum security: batch STARK proofs
   - Pharma selects security level when posting query (affects reward)
   - User's device decides proving strategy based on connectivity

3. **Optimistic aggregation server:**
   - Mobile device generates PLONK proof (fast, ~5s)
   - Off-chain aggregation server collects 100+ PLONK proofs
   - Server converts batch to single STARK proof (recursive composition)
   - Result: mobile UX stays fast; pharma gets STARK security guarantee
   - Tradeoff: trust in aggregation server (mitigated by fraud proofs)

4. **Wi-Fi gating for STARK submission:**
   - PLONK proofs: submitted over any network (cellular or Wi-Fi)
   - STARK proofs: queue until Wi-Fi available (configurable by user)
   - Implementation: `NWPathMonitor` constraint check before upload
   - User sees: "Your zk proof is ready. Uploading via Wi-Fi in background."

```rust
// v1.1+ STARK batching strategy
enum ProofStrategy {
    /// Fast single proof — submit immediately via any network
    PlonkDirect,
    /// Batch STARK — queue for Wi-Fi, submit as aggregated proof
    StarkBatched {
        batch_size: usize,
        pending_proofs: Vec<ZkProof>,
    },
    /// Optimistic — submit PLONK now, upgrade to STARK later via aggregator
    OptimisticUpgrade,
}

fn select_proof_strategy(
    connectivity: NetworkState, 
    requires_pq_security: bool,
) -> ProofStrategy {
    match (connectivity, requires_pq_security) {
        (WiFi, true) => ProofStrategy::StarkBatched { batch_size: 100, pending_proofs: vec![] },
        (Cellular, true) => ProofStrategy::OptimisticUpgrade,
        (_, false) => ProofStrategy::PlonkDirect,
    }
}
```
